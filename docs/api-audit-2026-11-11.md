# Аудит API Jacko — 11 ноября 2026

Проверены REST, аутентификация, сессии, сообщества, сообщения, вложения, WebSocket, outbox, миграции и зависимости. Изменения внесены в рабочее дерево. Рабочая база и запущенный экземпляр API не обновлялись: проверки использовали временные схемы PostgreSQL, отдельные Redis-топики и тестовые S3-объекты.

## Исправления

| Проблема | Изменение | Подтверждение |
|---|---|---|
| API собирался Go 1.26.5. `govulncheck` находил 17 известных уязвимостей стандартной библиотеки с достижимыми символами | Минимальная версия проекта поднята до Go 1.26.11. Обновлены `x/crypto`, `x/net`, `klauspost/compress` и связанные зависимости | Итоговый `govulncheck`: `No vulnerabilities found` |
| `WriteTimeout` ограничивал запись ответа, но большинство REST-запросов не передавали БД ограниченный срок работы | Общая обёртка REST: deadline 10 секунд, отмена контекста, `504 request_timeout`, общие приватные заголовки | Реальная блокировка строки канала: HTTP 504, сообщение отсутствует, повтор после снятия блокировки успешен |
| Ограничение параллельного Argon2 не ограничивало частоту попыток входа | Общий для регистрации/входа token bucket, отдельный для refresh; HTTP 429 и Retry-After; таблица ограничена 4096 адресами | Конкурентные запросы, восстановление лимита, очистка памяти, попытка обхода через forwarding-заголовки и IPv4-mapped IPv6 |
| Число принятых WebSocket-соединений не имело верхнего предела | 10 000 слотов на шлюз, включая неаутентифицированные соединения; HTTP 503 при заполнении | Проверка отказа при заполнении и освобождения слота после неуспешного подключения |
| История могла сканировать удалённые сообщения через общий индекс `(channel_id, id)` | Миграция `000009`: частичный индекс только по `deleted_at IS NULL` | EXPLAIN ANALYZE на 20 000 строках, из них 19 950 удалённых |
| Подписанная форма S3 разрешала до 8 МиБ даже при меньшем заявленном размере | Подписывается точный диапазон `size_bytes..size_bytes`; повторная проверка размера при complete сохранена | Проверка условий подписанной политики и загрузка в реальный локальный S3 |
| `/healthz` не отличал отвечающий процесс от API с недоступной БД | Добавлен `/readyz` с проверкой PostgreSQL за одну секунду; 204/503 | Проверки успеха, отказа, deadline и отсутствия внутренних данных в ответе |
| При ошибке одного HTTP-слушателя второй мог оставаться активным до завершения процесса | Добавлены закрытие API-сервера при выходе из `run` и отмена контекста запуска | Компиляция, `go vet`; отдельный сценарий отказа слушателя не автоматизирован |
| Заголовки принимались с большим стандартным пределом Go | `MaxHeaderBytes` API уменьшен до 16 КиБ, с внутренним дополнительным буфером Go | Проверка конфигурации; отдельный сетевой тест предела не добавлялся |
| Часть проверок выполнялась только вручную, обычный `go test` мог пропустить интеграционные сценарии | Добавлены автоматические сценарии сообществ и S3, единый скрипт полного прогона | 11 тестов верхнего уровня, 24 с подтестами; 0 ошибок и 0 пропусков |

В исходном коде существующие тесты проходили. Основные обнаруженные проблемы касались зависимостей, защиты ресурсов, эксплуатационной готовности и неполного покрытия автоматическими проверками. Подтверждённого обхода авторизации в исследованных сценариях не найдено.

Go 1.26.11 содержит исправления безопасности, включая `net/http`: [официальная история выпусков](https://go.dev/doc/devel/release#go1.26.0). Обнаружение достижимого символа сканером не доказывает практическую эксплуатацию конкретного endpoint; обновление устраняет соответствующие известные дефекты библиотек.

Исходные достижимые записи: GO-2026-5026, 5972, 6088, 6089, 6090, 6218, 6603, 6605, 6607, 6608, 6610, 6611, 6612, 6613, 6617, 6809, 6859. Дополнительно обновлены зависимости с предупреждениями на уровне модулей, без найденного вызова уязвимых символов: `x/net` 0.60.0 → 0.62.0, `x/crypto` 0.58.0 → 0.59.0, `klauspost/compress` 1.20.1 → 1.20.2.

## Проверки и скорость

Полный прогон: `./server/scripts/test-api.sh`. Среда: macOS arm64, Go 1.26.11, локальные PostgreSQL 17, Redis 7 и SeaweedFS 4.53 из Compose.

- `go test -race -count=1 -timeout=2m -v ./...` — PASS, 24 проверки с подтестами, без пропусков и сообщений о гонках.
- `go vet ./...` — PASS.
- `govulncheck v1.9.0 ./...` — известных уязвимостей не найдено.
- OpenAPI YAML успешно разобран; все 96 локальных `$ref` разрешаются. Это проверка синтаксиса и ссылок, не полная сертификация контракта.
- `git diff --check` — PASS.

Проверены повторные отправки, конфликт nonce, откат транзакции при отказе outbox, конкурентная ротация refresh, отзыв сессии, ответы/правки/удаления, восстановление пропущенных событий, повтор публикации после сбоя, два шлюза и presence. Новые проверки покрывают права владельца/участника/постороннего, приглашения и их срок, пагинацию каналов, PNG/JPEG, неверные типы и размеры, конкурентный complete, неизменность проверенного объекта после перезаписи staging, однократную привязку вложения и прекращение выдачи ссылок после удаления сообщения.

В последнем полном прогоне с race-инструментацией: 32 WebSocket-клиента, 8 отправителей, 200 сообщений, 6 400 доставок; p50 39,525 мс, p95 79,390 мс, p99 95,842 мс. `simulated publication failure` в журнале — намеренная проверка повтора outbox, а не ошибка прогона.

Из-за разброса задержек проведено отдельное сравнение без race-инструментации. Исходный код взят из HEAD в отдельную временную копию; обе версии запускались одним Go 1.26.11, последовательно, по три прогона на одном локальном стенде:

| Показатель | Исходный код | После изменений |
|---|---|---|
| p99, три прогона | 54,621 / 58,806 / 57,516 мс | 57,002 / 54,688 / 55,346 мс |
| Медиана p99 | 57,516 мс | 55,346 мс |
| Время 6 400 доставок | 215–220 мс | 222–229 мс |

Задержки доставки остаются сопоставимыми; эти короткие локальные прогоны не доказывают общего ускорения API. Индекс добавляет обслуживание при записи, зато устраняет сканирование удалённых строк при чтении.

В отдельном эксперименте истории: 20 000 строк / 19 950 удалённых, запрос одной страницы. Без частичного индекса — 0,756 мс и 328 обращений к буферам; с индексом — 0,018 мс и 2 обращения. Это результат конкретного запроса на локальном наборе данных, не коэффициент ускорения всего сервиса.

Полный журнал проверки и контрольных нагрузочных прогонов: [api-audit-test-results.txt](api-audit-test-results.txt).

## Вердикт архитектуры

**Подходящий модульный монолит для MVP и закрытой беты. Для открытого публичного запуска эксплуатационная и антиабьюз-защита пока недостаточны.**

Сильные стороны: PostgreSQL остаётся источником истины; сообщение, номер события и outbox сохраняются атомарно; nonce защищает от дублей; авторизация записи проверяется в транзакции; SQL параметризован; пароли используют Argon2id, токены — случайные секреты с хешами в БД; Redis не является единственной копией сообщения; WebSocket имеет ограниченную очередь и восстановление по курсору; слои HTTP, use case и PostgreSQL разделены. Переписывать это в микросервисы сейчас оснований нет.

Приоритеты перед публичным запуском:

1. Распределённые лимиты по пользователю/аккаунту/IP, квоты сообщений и хранилища, защита входного узла. Новый лимитер работает на одном процессе и использует адрес TCP-соединения. За прокси все клиенты делят его запас; нужна явная модель доверенных прокси. Не следует просто доверять входящему `X-Forwarded-For`.
2. Подтверждение email, восстановление пароля, модерация и отзыв доступа. Регистрация с ответом 409 позволяет узнать о существовании email. WebSocket повторно проверяет сессию и членство на heartbeat, поэтому отзыв не мгновенный.
3. Очистка истёкших сессий/приглашений, незавершённых загрузок, удалённых объектов и политика хранения журнала. Сейчас эти данные могут расти без ограничения. Уже выданные ссылки S3 живут до 60 секунд после удаления сообщения.
4. Миграции с учётом применённых версий, CI, проверенное восстановление резервной копии, TLS/прокси и мониторинг отказов. `/readyz` проверяет доступность БД, но не её схему и не все зависимости.
5. Нагрузочная проверка горячего канала и 10 000 соединений. Счётчик событий сериализует записи одного канала; общий Redis-топик доставляет все события всем шлюзам; хаб использует общий mutex; outbox удерживает транзакцию во время сетевой публикации. Это вероятные ограничения при росте, которые следует измерять до изменения архитектуры.

Гарантия outbox — повторяемая доставка после коммита, с возможными дублями; клиентский курсор устраняет повторы. При сетевом сбое во время коммита результат HTTP-запроса может остаться неизвестным: отправку следует повторять с тем же nonce. Проверки локального стенда не заменяют длительные испытания отказов PostgreSQL/Redis/S3, проверку контейнеров на уязвимости и проверку production-конфигурации.

## Применение

Нужно пересобрать и перезапустить API исправленным Go. Для существующей базы применить новую миграцию `000009_live_history_index.up.sql` после предыдущих миграций. Она проверена во временных схемах, но не применена к рабочей базе. Обычный `CREATE INDEX` блокирует записи на время построения; для большой работающей таблицы потребуется отдельное планирование online-миграции.

REST-контракты сохранены; добавлены ответы 429/504 и `/readyz`. Сроки и лимиты описаны в [серверной основе](server-foundation.md). При следующем изменении полный прогон выполняется одной командой из корня: `./server/scripts/test-api.sh`.
