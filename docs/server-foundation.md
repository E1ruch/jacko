# Серверная основа Jacko

HTTP API поддерживает отправку текстового сообщения и чтение истории. Обработчик получает идентификатор автора из проверенной сессии. WebSocket-шлюз проверяет сессию и доступ к каналу перед подпиской. PostgreSQL-адаптер сохраняет сообщение вместе с событием.

## Границы модулей

- `server/internal/messages` — команда отправки, модель сообщения, ошибки и контракт хранилища.
- `server/internal/messages/postgres` — запросы и граница транзакции.
- `server/internal/sessions` — проверка Bearer-токена и контракт хранилища сессий.
- `server/internal/httpapi` — маршруты, разбор запросов и HTTP-ошибки.
- `server/internal/outbox` — журнал событий канала, чтение для восстановления и публикация с повторами.
- `server/internal/realtime` — транспорт Redis и локальные подписки.
- `server/internal/gateway` — WebSocket-протокол, доступ к каналу и heartbeat.
- `server/cmd/api` — сборка зависимостей, запуск и остановка HTTP-сервера.
- `server/migrations` — версионируемая схема PostgreSQL.

Право записи сейчас определяется членством в сообществе. Перед появлением приватных каналов потребуется расширить проверку прав в той же границе транзакции.

## Гарантии записи

Подтверждение можно вернуть после коммита. Уникальность пары `(author_id, nonce)` защищает от дублей при параллельных запросах. Повтор с тем же каналом и содержимым возвращает существующую запись. Повтор с изменённым содержимым или каналом возвращает конфликт. Перед добавлением редактирования нужно хранить отпечаток первоначального запроса отдельно от изменяемого текста.

ID сообщений выдаёт PostgreSQL. В JSON идентификаторы передаются строками. ID используются для сортировки истории. Для восстановления используется отдельный `seq` канала. Счётчик, сообщение и событие обновляются одной транзакцией. Запись в один канал сериализуется на строке счётчика. Разные каналы используют независимые счётчики.

## Следующий шаг

Добавить метрики задержки, размера очередей и отставания outbox. Для длительного прогона определить срок хранения опубликованных событий и проверить переход на полную синхронизацию после очистки журнала. Проверять один популярный канал отдельно, поскольку записи в него конкурируют за один счётчик.

## Локальная проверка

Из корня проекта:

```sh
docker compose -f deploy/compose.yaml up -d --wait
cd server
JACKO_TEST_DATABASE_URL='postgres://jacko:jacko@127.0.0.1:5432/jacko?sslmode=disable' go test -race -v ./...
go vet ./...
```

Интеграционный тест применяет миграции в отдельной временной схеме и удаляет её после прогона. Учётные данные в Compose предназначены для локального стенда.

## Запуск HTTP API

Из корня проекта примените миграции к пустой локальной базе. При обновлении существующей базы остановите прежние процессы API и примените только отсутствующие миграции в порядке номеров. Миграция 000003 назначает курсоры существующим событиям и сохраняет их статус публикации.

```sh
for migration in server/migrations/*.up.sql; do
  docker compose -f deploy/compose.yaml exec -T postgres \
    psql -v ON_ERROR_STOP=1 -U jacko -d jacko < "$migration" || break
done
```

Для ручной проверки в отдельном терминале создайте пользователя, сообщество, канал и временную сессию. Выполняйте команды из корня проекта. Сохраните терминал для запросов ниже.

```sh
jacko_token=$(openssl rand -hex 32)
jacko_channel=$(docker compose -f deploy/compose.yaml exec -T postgres \
  psql -qAt -v ON_ERROR_STOP=1 -U jacko -d jacko <<SQL
BEGIN;
INSERT INTO users DEFAULT VALUES RETURNING id AS user_id \gset
INSERT INTO guilds (name) VALUES ('Demo') RETURNING id AS guild_id \gset
INSERT INTO members (guild_id, user_id) VALUES (:guild_id, :user_id);
INSERT INTO sessions (token_hash, user_id, expires_at)
VALUES (sha256(decode('$jacko_token', 'hex')), :user_id, now() + interval '1 hour');
INSERT INTO channels (guild_id, name) VALUES (:guild_id, 'general') RETURNING id;
COMMIT;
SQL
)
```

В другом терминале запустите API:

```sh
cd server
JACKO_DATABASE_URL='postgres://jacko:jacko@127.0.0.1:5432/jacko?sslmode=disable' go run ./cmd/api
```

В терминале с созданной сессией:

```sh
jacko_messages_url="http://127.0.0.1:8080/api/v1/channels/$jacko_channel/messages"
curl --fail-with-body "$jacko_messages_url" \
  -H "Authorization: Bearer $jacko_token" \
  -H 'Content-Type: application/json' \
  --data '{"nonce":"demo-1","content":"Привет, Jacko!"}'
curl --fail-with-body "$jacko_messages_url?limit=20" \
  -H "Authorization: Bearer $jacko_token"
```

История возвращается от новых сообщений к старым. Значение `next_before` передаётся как `before` следующего запроса. Размер страницы по умолчанию 50, максимум 100. Пустой канал возвращает пустой массив. Канал без доступа возвращает тот же статус 404, что и отсутствующий канал.

Сессии имеют срок действия и могут быть отозваны через `revoked_at`. База хранит SHA-256 от 32 случайных байтов токена. Пока сессии создаются вручную для стенда. Регистрация, вход и выпуск сессий через HTTP появятся отдельным этапом.

## WebSocket-доставка

Для живых событий запустите API с `JACKO_REDIS_URL=redis://127.0.0.1:6379/0`. PostgreSQL и Redis запускаются через `docker compose -f deploy/compose.yaml up -d --wait`. Узлы одного окружения используют общий PostgreSQL, Redis и одинаковое значение `JACKO_REDIS_TOPIC`. Для разных окружений задайте разные темы. По умолчанию тема — `jacko:v1:messages`.

1. Клиент подключается к `/api/v1/channels/{id}/events` с того же origin, где опубликован API.
2. При первом подключении клиент передаёт `{"op":"identify","token":"<session token>"}` в течение пяти секунд. Шлюз проверяет сессию и право читать канал до отправки данных.
3. Шлюз отвечает `{"v":1,"op":"ready","cursor":"42"}`. При первом подключении клиент запрашивает историю через HTTP и объединяет её с поступающими событиями по ID сообщения. После загрузки истории клиент сохраняет начальный курсор и продвигает его по мере применения кадров.
4. Клиент отправляет сообщения через HTTP. Шлюз передаёт кадры вида `{"v":1,"op":"dispatch","event_id":"17","seq":"43","t":"MESSAGE_CREATE","d":{…}}`. Курсор хранится отдельно для каждого канала как строка. Клиент сохраняет последнюю применённую последовательность.
5. При переподключении клиент добавляет к `identify` поле `"after":"43"`. Шлюз выдаёт пропущенные события по порядку, затем отправляет `ready` с актуальным курсором и продолжает живую доставку. Можно воспроизвести до 256 событий за раз. При слишком старом или будущем курсоре шлюз отправляет `resync_required`. Клиент повторяет подключение без `after` и загружает актуальную историю.

Воркер берёт пакеты до 32 событий с блокировкой `SKIP LOCKED`. Подтверждение HTTP зависит от коммита в PostgreSQL. Если публикация не удалась, воркер повторяет попытку. Шлюз пропускает уже переданные последовательности и дочитывает пропуски из журнала при получении следующего события. Раз в 20 секунд heartbeat перепроверяет сессию, членство и последнее записанное событие. Это позволяет восстановить даже пропуск в конце потока. При заполнении очереди шлюз отключает медленного клиента, который может переподключиться со своим курсором.

Для проверки доставки между двумя шлюзами:

```sh
cd server
JACKO_TEST_DATABASE_URL='postgres://jacko:jacko@127.0.0.1:5432/jacko?sslmode=disable' \
JACKO_TEST_REDIS_URL='redis://127.0.0.1:6379/0' go test -race -v ./...
```

Для локального замера добавьте `JACKO_TEST_LOAD=1` и запустите `go test -count=3 -v ./internal/messages/postgres` без `-race`. В каждом прогоне 8 параллельных отправителей записывают 200 сообщений в один канал. 32 WebSocket-клиента на двух шлюзах проверяют порядок всех 6 400 доставок. Задержка измеряется от начала HTTP-запроса до чтения WebSocket-события клиентом.
