# Серверная основа Jacko

HTTP API поддерживает отправку текстового сообщения и чтение истории. Обработчик получает идентификатор автора из проверенной сессии. WebSocket-шлюз проверяет сессию и доступ к каналу перед подпиской. PostgreSQL-адаптер сохраняет сообщение вместе с событием.

## Границы модулей

- `server/internal/messages` — команда отправки, модель сообщения, ошибки и контракт хранилища.
- `server/internal/messages/postgres` — запросы и граница транзакции.
- `server/internal/accounts` — регистрация и проверка паролей.
- `server/internal/communities` — сообщества, каналы, членство и приглашения.
- `server/internal/attachments` — загрузка, проверка и выдача изображений через S3.
- `server/internal/sessions` — выпуск, проверка, ротация и отзыв токенов.
- `server/internal/httpapi` — маршруты, разбор запросов и HTTP-ошибки.
- `server/internal/outbox` — журнал событий канала, чтение для восстановления и публикация с повторами.
- `server/internal/realtime` — транспорт Redis и локальные подписки.
- `server/internal/gateway` — WebSocket-протокол, доступ к каналу и heartbeat.
- `server/internal/telemetry` — реестр Prometheus и измерение времени HTTP-запросов.
- `server/cmd/api` — сборка зависимостей, запуск и остановка HTTP-сервера.
- `server/migrations` — версионируемая схема PostgreSQL.

Право записи сейчас определяется членством в сообществе. Перед появлением приватных каналов потребуется расширить проверку прав в той же границе транзакции.

## Гарантии записи

Подтверждение можно вернуть после коммита. Уникальность пары `(author_id, nonce)` защищает от дублей при параллельных запросах. Повтор исходного запроса возвращает актуальную версию сообщения. Хеш исходного текста хранится отдельно, чтобы повторы продолжали работать после правки. Другой исходный текст, канал или `reply_to` при том же `nonce` дают конфликт. После удаления повтор возвращает 404, а `nonce` остаётся занятым.

ID сообщений выдаёт PostgreSQL. В JSON идентификаторы передаются строками. ID используются для сортировки истории. Для восстановления используется отдельный `seq` канала. Счётчик, сообщение и событие обновляются одной транзакцией. Запись в один канал сериализуется на строке счётчика. Разные каналы используют независимые счётчики.

## Локальная проверка

Из корня проекта:

```sh
docker compose -f deploy/compose.yaml up -d --wait
cd server
JACKO_TEST_DATABASE_URL='postgres://jacko:jacko@127.0.0.1:5432/jacko?sslmode=disable' go test -race -v ./...
go vet ./...
```

Интеграционный тест применяет миграции в отдельной временной схеме и удаляет её после прогона. Учётные данные в Compose предназначены для локального стенда.

## Запуск HTTP API

Из корня проекта примените миграции к пустой локальной базе. При обновлении существующей базы остановите прежние процессы API и примените только отсутствующие миграции в порядке номеров. Миграция 000003 назначает курсоры существующим событиям и сохраняет их статус публикации.

```sh
for migration in server/migrations/*.up.sql; do
  docker compose -f deploy/compose.yaml exec -T postgres \
    psql -v ON_ERROR_STOP=1 -U jacko -d jacko < "$migration" || break
done
```

Для ручной проверки в отдельном терминале создайте пользователя, сообщество, канал и временную сессию. Выполняйте команды из корня проекта. Сохраните терминал для запросов ниже.

```sh
jacko_token=$(openssl rand -hex 32)
jacko_channel=$(docker compose -f deploy/compose.yaml exec -T postgres \
  psql -qAt -v ON_ERROR_STOP=1 -U jacko -d jacko <<SQL
BEGIN;
INSERT INTO users DEFAULT VALUES RETURNING id AS user_id \gset
INSERT INTO guilds (name) VALUES ('Demo') RETURNING id AS guild_id \gset
INSERT INTO members (guild_id, user_id) VALUES (:guild_id, :user_id);
INSERT INTO sessions (token_hash, user_id, expires_at)
VALUES (sha256(decode('$jacko_token', 'hex')), :user_id, now() + interval '1 hour');
INSERT INTO channels (guild_id, name) VALUES (:guild_id, 'general') RETURNING id;
COMMIT;
SQL
)
```

В другом терминале запустите API из корня проекта. При первом запуске создайте локальный файл из шаблона:

```sh
test -f .env || (umask 077; cp .env.example .env)
set -a
. ./.env
set +a
cd server
go run ./cmd/api
```

`.env.example` содержит параметры локального Docker-стенда для PostgreSQL, Redis и S3. Go читает экспортированные переменные окружения. Локальный `.env` игнорируется Git. Если файл создан до добавления вложений, перенесите из шаблона строки `JACKO_S3_*`.

В терминале с созданной сессией:

```sh
jacko_messages_url="http://127.0.0.1:8080/api/v1/channels/$jacko_channel/messages"
curl --fail-with-body "$jacko_messages_url" \
  -H "Authorization: Bearer $jacko_token" \
  -H 'Content-Type: application/json' \
  --data '{"nonce":"demo-1","content":"Привет, Jacko!"}'
curl --fail-with-body "$jacko_messages_url?limit=20" \
  -H "Authorization: Bearer $jacko_token"
```

История возвращается от новых сообщений к старым. Значение `next_before` передаётся как `before` следующего запроса. Размер страницы по умолчанию 50, максимум 100. Пустой канал возвращает пустой массив. Канал без доступа возвращает тот же статус 404, что и отсутствующий канал.

## Учётные записи и сессии

Реализованные REST-операции описаны в [OpenAPI](../api-schema/openapi.yaml).

| Метод и путь | Поведение |
|---|---|
| `POST /api/v1/auth/register` | Принимает `email` и `password`, возвращает `user_id`. |
| `POST /api/v1/auth/login` | Принимает `email` и `password`, выпускает отдельную сессию и возвращает пару токенов. |
| `POST /api/v1/auth/refresh` | Принимает `refresh_token` и атомарно заменяет оба токена сессии. |
| `GET /api/v1/auth/session` | Принимает access-токен в заголовке Bearer и возвращает `user_id`. |
| `DELETE /api/v1/auth/session` | Отзывает сессию по access-токену. |

Пароли хранятся как Argon2id-хеши с уникальной солью. База хранит SHA-256 от случайных секретов токенов. Access-токен действует до 15 минут, refresh-токен — до 30 дней с момента входа. При обновлении абсолютный срок сессии сохраняется. Клиенту нужно выполнять один запрос обновления на сессию за раз и переподключать WebSocket с новым access-токеном. Старые сессии, созданные до миграции, действуют до своего срока и не обновляются через refresh.

Регистрация и вход сейчас предназначены для стенда. Подтверждение email, сброс пароля и распределённые лимиты запросов остаются в плане до публичного запуска.

## Сообщества и приглашения

Все маршруты требуют Bearer access-токен.

| Метод и путь | Поведение |
|---|---|
| `POST /api/v1/guilds` | Принимает `name`. Создаёт сообщество, членство владельца и канал `general` одной транзакцией. |
| `GET /api/v1/guilds` | Возвращает сообщества пользователя. |
| `POST /api/v1/guilds/{guild}/channels` | Владелец создаёт текстовый канал по `name`. |
| `GET /api/v1/guilds/{guild}/channels` | Участник получает текстовые каналы сообщества. |
| `POST /api/v1/guilds/{guild}/invites` | Владелец выпускает приглашение на семь дней. |
| `POST /api/v1/invites/redeem` | Принимает `token` и возвращает сообщество. Повторное вступление по действующему приглашению сохраняет одно членство. |

Списки содержат до 100 записей. Для следующей страницы передайте `next_after` в параметре `after`. Приглашение можно использовать повторно до истечения срока. В базе хранится только хеш токена. У сообществ, созданных до миграции 000006, членства сохраняются. Назначение владельца для таких сообществ требует отдельного решения.

## Изображения в сообщениях

Docker Compose запускает приватный S3-бакет через SeaweedFS. `JACKO_S3_URL` должен быть доступен API и клиенту, поскольку используется в подписанных URL. API вложений включается при заданном `JACKO_S3_URL`.

1. Участник канала отправляет `POST /api/v1/channels/{channel}/attachments` с `media_type` и `size_bytes`. Разрешены JPEG и PNG до 8 МиБ.
2. Клиент отправляет `multipart/form-data` на полученный S3 URL. Сначала передаёт все поля из `fields`, затем добавляет файл в поле `file`. Форма действительна десять минут.
3. Загрузивший пользователь вызывает `POST /api/v1/attachments/{id}/complete`. API проверяет длину, формат и декодируемость, ограничивает каждую сторону 4096 пикселями и суммарный размер 12 мегапикселями. Проверенные байты копируются в отдельный ключ. Подписанная форма не даёт доступа к этому ключу.
4. Клиент передаёт `attachment_id` в запросе отправки сообщения. Одно изображение привязывается к одному сообщению. Подпись необязательна. Идентификатор сохраняется в истории и событиях WebSocket.
5. Участник канала вызывает `GET /api/v1/attachments/{id}` и получает размеры, тип и URL скачивания на 60 секунд. После удаления сообщения API перестаёт выдавать новые ссылки. Выданные ранее ссылки действуют до истечения срока.

Генерация превью и автоматическая очистка незавершённых загрузок и удалённых объектов запланированы перед длительной эксплуатацией.

## WebSocket-доставка

Сообщение можно отправить с необязательным `reply_to`, переданным строкой. Новые ответы принимаются только на существующие сообщения того же канала. Если исходное сообщение удалено позже, ссылка остаётся доступной в ответе.

Автор может обновить текст через `PATCH /api/v1/channels/{channel}/messages/{message}` и удалить сообщение через `DELETE` по тому же пути. Правка возвращает актуальное сообщение с `edited_at` и публикует `MESSAGE_UPDATE`. Повтор правки с тем же текущим текстом сохраняет исходную отметку времени. Удаление возвращает 204, исключает сообщение из истории и публикует `MESSAGE_DELETE` с полями `id`, `channel_id` и `deleted_at`. Повторное удаление также возвращает 204.

После удаления более ранние записи об этом сообщении в журнале содержат `MESSAGE_DELETE` с прежними номерами последовательности и без текста. Клиент применяет такое событие идемпотентно, включая случай, когда сообщения нет в локальной истории.

Для живых событий запустите API с `JACKO_REDIS_URL=redis://127.0.0.1:6379/0`. PostgreSQL и Redis запускаются через `docker compose -f deploy/compose.yaml up -d --wait`. Узлы одного окружения используют общий PostgreSQL, Redis и одинаковое значение `JACKO_REDIS_TOPIC`. Для разных окружений задайте разные темы. По умолчанию тема — `jacko:v1:messages`.

1. Клиент подключается к `/api/v1/channels/{id}/events` с того же origin, где опубликован API.
2. При первом подключении клиент передаёт `{"op":"identify","token":"<session token>"}` в течение пяти секунд. Шлюз проверяет сессию и право читать канал до отправки данных.
3. Шлюз отвечает `{"v":1,"op":"ready","cursor":"42"}`. При первом подключении клиент запрашивает историю через HTTP и объединяет её с поступающими событиями по ID сообщения. После загрузки истории клиент сохраняет начальный курсор и продвигает его по мере применения кадров.
4. Клиент отправляет сообщения через HTTP. Шлюз передаёт кадры вида `{"v":1,"op":"dispatch","event_id":"17","seq":"43","t":"MESSAGE_CREATE","d":{…}}`. Курсор хранится отдельно для каждого канала как строка. Клиент сохраняет последнюю применённую последовательность.
5. При переподключении клиент добавляет к `identify` поле `"after":"43"`. Шлюз выдаёт пропущенные события по порядку, затем отправляет `ready` с актуальным курсором и продолжает живую доставку. Можно воспроизвести до 256 событий за раз. При слишком старом или будущем курсоре шлюз отправляет `resync_required`. Клиент повторяет подключение без `after` и загружает актуальную историю.

Воркер берёт пакеты до 32 событий с блокировкой `SKIP LOCKED`. Подтверждение HTTP зависит от коммита в PostgreSQL. Если публикация не удалась, воркер повторяет попытку. Шлюз пропускает уже переданные последовательности и дочитывает пропуски из журнала при получении следующего события. Раз в 20 секунд heartbeat перепроверяет сессию, членство и последнее записанное событие. Это позволяет восстановить даже пропуск в конце потока. При заполнении очереди шлюз отключает медленного клиента, который может переподключиться со своим курсором.

Для проверки доставки между двумя шлюзами:

```sh
cd server
JACKO_TEST_DATABASE_URL='postgres://jacko:jacko@127.0.0.1:5432/jacko?sslmode=disable' \
JACKO_TEST_REDIS_URL='redis://127.0.0.1:6379/0' go test -race -v ./...
```

Для локального замера добавьте `JACKO_TEST_LOAD=1` и запустите `go test -count=3 -v ./internal/messages/postgres` без `-race`. В каждом прогоне 8 параллельных отправителей записывают 200 сообщений в один канал. 32 WebSocket-клиента на двух шлюзах проверяют порядок всех 6 400 доставок. Задержка измеряется от начала HTTP-запроса до чтения WebSocket-события клиентом.

## Метрики стенда

Добавьте к окружению API `JACKO_METRICS_ADDR=127.0.0.1:9090`. Метрики будут доступны по `http://127.0.0.1:9090/metrics` на отдельном слушателе. Для удалённого сбора используйте адрес внутренней сети. Стандартные коллекторы экспортируют метрики процесса и Go runtime.

| Метрика | Что измеряет |
|---|---|
| `jacko_http_request_duration_seconds` | Длительность отправки и чтения истории с разбивкой по операции и HTTP-статусу. |
| `jacko_ws_connections`, `jacko_ws_queued_events` | Активные подписки и суммарная глубина очередей на узле. |
| `jacko_ws_queue_overflows_total`, `jacko_ws_resync_required_total` | Отключения из-за заполнения очереди и запросы полной синхронизации. |
| `jacko_ws_dispatch_total` | Успешно записанные WebSocket-кадры, отдельно для живых событий и восстановления. |
| `jacko_ws_live_delivery_seconds` | Время от получения события из Redis на шлюзе до завершения записи кадра. Время на HTTP, PostgreSQL и отрисовку измеряется отдельно. |
| `jacko_outbox_batch_duration_seconds`, `jacko_outbox_publish_failures_total` | Длительность публикации пакетов и число неудачных попыток. |
| `jacko_outbox_oldest_pending_seconds`, `jacko_outbox_probe_ok` | Возраст самого старого неопубликованного события в общей БД и статус замера. Воркер обновляет показатели каждые пять секунд. Для общей БД используйте максимум по узлам. |

Пример p99 для участка Redis → WebSocket:

```promql
histogram_quantile(0.99, sum by (le) (rate(jacko_ws_live_delivery_seconds_bucket[5m])))
```
