## Контекст проекта

Jacko — приложение для общения в сообществах. Первая версия веб-клиента ориентирована на десктоп и адаптируется к мобильному браузеру. Визуальная основа — светлый интерфейс, мятные акценты, спокойная типографика и компоновка из макета. Цель продукта — быстрый отклик на действия, плавная лента и предсказуемое восстановление после обрыва сети.

Бэкенд уже реализован на Go. PostgreSQL хранит сообщения и журнал событий, Redis используется для живой доставки и онлайн-статусов, S3 — для изображений. Готовы учётные записи, сообщества, инвайты, история, отправка и изменения сообщений, вложения и жалобы. В локальной приёмке один шлюз удержал 10 000 соединений и доставил 50 000 событий по порядку за прогон. p99 составил 231–445 мс до чтения WebSocket-события. Серверные задержки дальше наблюдаем через Prometheus. На момент подготовки плана каталога `client/` ещё нет. [Протокол приёмки](backend-acceptance.md)

## Предлагаемая компоновка

На десктопе — навигация по сообществам, список текстовых каналов выбранного сообщества и центральная лента с закреплённым полем ввода. Участники открываются в сворачиваемой панели. На узких экранах список каналов и чат становятся отдельными экранами с понятным возвратом. Мятный акцент выделяет выбранный канал и основное действие. Голос, ЛС, реакции, поиск и оболочка Tauri относятся к последующим этапам.

Для первого сценария достаточно экранов входа и регистрации, списка сообществ и каналов, чата и принятия приглашения. Для каждого нужны состояния загрузки, пустого результата, отсутствия доступа и ошибки. В чате отдельно показать восстановление связи и статус отправки. Навигация и отправка доступны с клавиатуры, фокус заметен, а ошибка привязана к полю или действию.

## Детали для первого рабочего среза

- **Сессии.** Передавай access-токен как Bearer. Выполняй только один запрос refresh одновременно для каждой сессии. После ротации переподключай WebSocket с новым токеном. Для первого среза предлагается держать токены в памяти и запрашивать вход после перезагрузки страницы. Токены исключи из URL, логов и кэша сообщений. При выходе очисти состояние аккаунта и его локальный кэш.
- **История.** `GET /api/v1/channels/{channel}/messages` возвращает новые сообщения первыми. Старые страницы загружай через `before=next_before`. Храни идентификаторы и курсоры строками, а для числового сравнения используй точное представление. Привязывай запрос и буфер событий к активному каналу. При переключении отменяй старые запросы и закрывай старую подписку.
- **Первое подключение.** Открой `/api/v1/channels/{id}/events` и в течение пяти секунд отправь `identify` с access-токеном. После `ready` загрузи историю, буферизуя входящие кадры. Объедини историю с кадрами по ID и примени изменения по `seq`. Для восстановления сохраняй курсор вместе с согласованным состоянием. Если состояние кэша и курсор расходятся, загрузи историю заново.
- **Переподключение.** Передай `after` с последней применённой последовательностью. Кадры восстановления могут прийти до `ready`. На `resync_required` подключись без `after` и перестрой состояние из актуальной истории. Применяй удаления идемпотентно, даже если записи уже нет. Повторяй подключение с экспоненциальной задержкой и случайным разбросом.
- **Оптимистичная отправка.** Генерируй один `nonce` на сообщение и сохраняй его при повторе запроса. Текущий ответ REST и событие WebSocket содержат серверный ID, но не возвращают `nonce`. Свяжи временную запись с HTTP-ответом, затем объедини её с уже полученным WebSocket-событием по серверному ID. Учти оба порядка доставки и потерю HTTP-ответа. Одинаковый текст может принадлежать разным сообщениям.
- **Вложения.** Запроси подписанную форму у API канала, отправь поля формы и файл напрямую в S3, вызови `complete` и передай `attachment_id` при отправке сообщения. Загружай изображения по мере приближения к видимой области и резервируй место по размерам, которые возвращает API. На стенде проверь доступность адреса S3 и CORS из браузера. Ссылку на просмотр обновляй по мере истечения срока.

## Локальный стенд

Из корня проекта подними инфраструктуру командой `docker compose -f deploy/compose.yaml up -d --wait`. Проверь состояние схемы перед запуском API. На пустой БД примени миграции по порядку. Для существующей БД используй только недостающие миграции. Подробный порядок описан в [серверной документации](server-foundation.md#запуск-http-api).

В отдельном терминале из корня проекта загрузи локальные переменные и запусти API, если он ещё не работает:

```sh
test -f .env || (umask 077; cp .env.example .env)
set -a
. ./.env
set +a
cd server
go run ./cmd/api
```

Локальный API по умолчанию доступен на `127.0.0.1:8080`. Проверь `/readyz`. Для первого сценария подходят два тестовых аккаунта в разных браузерных контекстах. Если включён SMTP, коды для локальной проверки доступны в Mailpit на `127.0.0.1:8025`. Метрики сервера доступны на `127.0.0.1:9090/metrics`, когда включён отдельный слушатель метрик.

## Цели производительности

- Начальный JS — менее **300 КБ gzip**. Отдельно фиксировать размер начальной загрузки production-сборки.
- Холодный старт до интерактивного UI — менее **1 с**. Указывать устройство, браузер, режим сети и состояние кэша.
- Локальная доставка до отображения у получателя — менее **100 мс** как цель архитектуры. Замерять также локальный отклик после Enter и время до подтверждения. Серверные метрики и браузерное время отрисовки записывать отдельно.
- Прокрутка — ориентир **60 FPS** на дисплее 60 Гц. Проверять длинную историю с медиа при поступлении новых событий. Фиксировать длинные кадры и сдвиги позиции.
