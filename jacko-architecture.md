# jacko: архитектура (рабочее название)

Аналог Discord для СНГ. Начинаем с минимального функционала, но фундамент закладываем так, чтобы не переделывать при росте.

---

## 1. Цели и нефункциональные требования

Это цели для проверки нагрузочными тестами, а не гарантии.

| Область | Цель |
|---|---|
| Доставка сообщения (локально) | < 100 мс от отправки до отображения у получателя |
| Доставка сообщения (прод, p99) | < 300 мс внутри региона |
| Один узел шлюза (WS) | 10 000+ одновременных соединений на MVP-железе |
| Холодный старт клиента | < 1 с до интерактивного UI |
| RAM клиента в простое (десктоп) | < 100 МБ |
| Начальный JS веб-клиента | < 300 КБ gzip |
| Прокрутка списка сообщений | стабильные 60 FPS, без подвисаний на тысячах сообщений |
| Доступность | graceful degradation: падение Redis или S3 не роняет весь сервис |

---

## 2. Принципы

1. **Postgres источник истины.** Redis ускоряет и разгружает, но не хранит единственную копию данных.
2. **Протокол описан отдельно от кода.** Любой компонент можно переписать (например, шлюз на Rust) без переделки остального.
3. **Stateless-бэкенд.** Состояние в Postgres/Redis, поэтому узлы добавляются горизонтально.
4. **Backpressure везде.** Медленный клиент не должен тормозить сервер.
5. **Лёгкий клиент.** Рендерим только видимое, обновляем пачками, кэшируем локально.
6. **Всё своё.** Никаких внешних CDN, шрифтов и скриптов (устойчивость к блокировкам и приватность).
7. **Схема данных с запасом.** Таблицы и протокол сразу готовы к ЛС, реакциям, голосу, даже если в UI их ещё нет.

---

## 3. Стек

**Бэкенд:** Go 1.22+, chi (HTTP), coder/websocket, PostgreSQL (pgx + sqlc, golang-migrate, PgBouncer), Redis (go-redis), MinIO/S3, JWT, slog, Prometheus, Docker Compose.

**Клиент:** Svelte 5 + TypeScript + Vite (SPA). Работает в браузере и внутри Tauri 2 (Windows, macOS) из одной кодовой базы. Платформозависимое (уведомления, хранение токенов, трей, автообновление) за интерфейсом-адаптером: `web` и `tauri`.

**Голос (позже):** LiveKit (SFU на Go) как отдельный сервис, токены доступа выдаёт бэкенд.

## 4. Общая схема

```
 Клиенты (Web / Tauri)
        │  HTTPS (REST)        WSS (события)
        ▼                           ▼
 ┌─────────────┐          ┌──────────────────┐
 │  API-узлы   │          │ Gateway-узлы (WS)│  ← масштабируются горизонтально
 └──────┬──────┘          └────────┬─────────┘
        │                          │
        │        ┌─────────────────┴───────────────┐
        │        │ Redis: Pub/Sub, Streams,        │
        │        │ presence, rate limit, кэш       │
        │        └─────────────────┬───────────────┘
        ▼                          ▼
   PostgreSQL (primary + реплики)   MinIO / S3 (файлы, presigned URL)
```

На старте API и Gateway могут быть одним бинарником. В коде их границы сразу разделены, чтобы потом развести по отдельным процессам.

```

      snowflake/  ratelimit/  config/  observability/
    migrations/
    sqlc.yaml
  client/
    src/
      lib/api/          # сгенерированный клиент + типы
      lib/ws/           # WS-клиент, resume, backoff

      lib/platform/     # адаптеры: web.ts, tauri.ts

  deploy/               # docker-compose, конфиги

```

## 6. Данные

### 6.1 Идентификаторы
- 64-битные **Snowflake** (время + worker id + sequence): упорядочены по времени, не требуют обращения к БД, годятся для шардирования.
- В JSON и WS всегда **строками** (JS теряет точность на int64).
- Курсорная пагинация по ID (`before`, `after`, `limit`), без OFFSET.

### 6.2 Основные таблицы
- `users`, `sessions` (по устройствам, refresh-токены)
- `guilds`, `members`, `roles`, `member_roles`
- `channels` (тип: `text`, `voice`, `dm`, `category`; позиция, parent_id)
- `channel_overwrites` (права на уровне канала)
- `messages` (`id`, `channel_id`, `author_id`, `content`, `reply_to`, `edited_at`, `deleted_at`, `flags`)
- `attachments` (ключ в S3, mime, размер, ширина/высота)
- `reactions`, `invites`

### 6.3 Индексы и производительность
- Главный индекс сообщений: `(channel_id, id DESC)`.
- Партиционирование `messages` по диапазону ID (по времени), чтобы старые данные не раздували горячие индексы.
- Соединения через PgBouncer, пул в приложении ограничен.
- Никаких N+1: авторы и вложения подгружаются пакетно.
- Чтение истории в первую очередь с реплик, запись в primary.
- Репозитории скрыты за интерфейсами: хранилище сообщений при необходимости можно заменить (например, на Scylla) без переписывания логики.

---

## 7. Права доступа

- Роли с **битовой маской** разрешений + **переопределения на уровне канала**.
- Вся проверка в одном месте (`permissions`), никаких ad-hoc проверок в хендлерах.
- В UI MVP достаточно owner/member, но модель полная с первого дня.

---

## 8. API и протокол

### 8.1 REST
- OpenAPI-спецификация в `api-schema/`, из неё генерируются Go-хендлеры/типы и TS-клиент.
- Версионирование `/api/v1`.
- Единый формат ошибок, коды, request-id.

### 8.2 WebSocket-протокол
Конверт события:

```json
{ "v": 1, "op": "dispatch", "t": "MESSAGE_CREATE", "seq": 1042, "d": { } }
```

- **Handshake:** `identify` (токен) или `resume` (`session_id`, `last_seq`).
- **Heartbeat:** клиент шлёт ping по интервалу от сервера, сервер закрывает «мёртвые» соединения.
- **Resume:** после обрыва клиент присылает последний `seq`, сервер доотправляет пропущенное из Redis Streams. Если буфер не покрывает пропуск, клиент делает полную пересинхронизацию.
- **Идемпотентность:** при отправке клиент добавляет `nonce`; сервер дедуплицирует и возвращает то же сообщение, а клиент заменяет оптимистичную копию.
- **Ограничения:** максимальный размер фрейма, лимит событий в секунду на соединение.
- Формат JSON на MVP; схема событий описана так, что переход на бинарный формат (например, protobuf) возможен позже.

## 9. Роль Redis

| Задача | Механизм |
|---|---|
| Рассылка событий между узлами шлюза | Pub/Sub; узел подписывается только на гильдии, где у него есть подключённые участники |
| Resume-буфер | Streams с ограничением по длине и TTL (Pub/Sub теряет сообщения, Streams нет) |
| Presence | ключи с TTL + heartbeat; для больших гильдий presence отдаётся лениво (только для видимых участников) |
| Rate limiting | токен-бакет/скользящее окно на пользователя, IP, канал |
| Кэш | последние сообщения канала, права, профили |

При недоступности Redis сервис продолжает работать в деградированном режиме: запись в Postgres идёт, realtime между узлами и resume временно ограничены.

## 10. Бэкенд: как держим нагрузку

### 10.1 Путь отправки сообщения
1. Клиент отправляет сообщение (WS или REST) с `nonce`.
2. Валидация, проверка прав, rate limit.
3. Генерация Snowflake ID.
4. Запись в Postgres.
5. Публикация события в Redis (Pub/Sub для живой рассылки + запись в Stream).
6. Подтверждение отправителю, рассылка подписчикам.

Если запись в БД станет узким местом, добавляем пакетную запись и очередь без изменения протокола.

### 10.2 Gateway
- На соединение: одна горутина-читатель и одна горутина-писатель.
- Исходящая очередь **ограничена**; при переполнении медленный клиент отключается (он вернётся через resume).
- Ping/pong, таймауты чтения и записи, `context` везде.
- Graceful shutdown: перед остановкой узел сообщает клиентам о переподключении, чтобы не создавать шторм.
- Рассылка в большие гильдии батчится, события одного типа агрегируются.
- Переподключения клиентов с **jitter**, чтобы после рестарта не было лавины.

### 10.3 Масштабирование по этапам
1. **Один узел** (API + Gateway) + Postgres + Redis + MinIO.
2. **Несколько узлов Gateway** за балансировщиком, API отдельно; read-реплики Postgres.
3. **Рост дальше:** шардирование шлюзов по гильдиям, отдельное хранилище сообщений (по необходимости), горячие участки (шлюз) можно переписать на Rust, не меняя протокол.

---

## 11. Файлы
- Загрузка **напрямую в S3 по presigned URL**, бэкенд файлы не проксирует.
- Лимиты размера и типов, проверка mime.
- Превью изображений генерируются асинхронно; в метаданных хранятся ширина и высота (клиент резервирует место, список не «прыгает»).
- Раздача через собственный домен/CDN, не через сторонние сервисы.

---

## 12. Авторизация и безопасность
- Пароли: **argon2id**.
- Access-токен короткоживущий, refresh с **ротацией**, сессии по устройствам, возможность отозвать сессию.
- Email-подтверждение и сброс пароля.
- Провайдер авторизации абстрагирован (позже вход через Telegram/VK/телефон).
- Rate limits на логин, регистрацию, отправку сообщений.
- Санитизация markdown (защита от XSS), строгий CSP.
- Tauri: минимальные capabilities, без лишних разрешений.
- Валидация всех входных данных, лимиты размера сообщений.
- Защита WS от флуда (лимит событий, отключение нарушителей).

## 13. Клиент: как не лагать

### 13.1 Рендеринг
- **Виртуализация** списка сообщений (в DOM только видимые + небольшой запас), кэш измеренных высот строк.
- Svelte 5 с точечной реактивностью: обновляется только изменившийся элемент.
- Входящие события **батчатся по кадру** (`requestAnimationFrame`), а не применяются по одному.
- Картинки: ленивая загрузка, заранее известные размеры, без сдвигов раскладки.
- Тяжёлый markdown/эмодзи рендерится лениво и кэшируется.
- Анимации только на `transform`/`opacity`.

### 13.2 Состояние и данные
- **Нормализованный стор** (сущности по ID), списки хранят только идентификаторы.
- **Оптимистичная отправка**: сообщение показывается сразу, потом заменяется подтверждённым по `nonce`.
- Локальный кэш в **IndexedDB** (последние сообщения каналов, серверы, профили) для мгновенного открытия.
- Ограничение памяти: в RAM держим ограниченное число сообщений на канал, остальное подгружаем.
- Парсинг WS и работа с IndexedDB вне главного потока (Web Worker), где это даёт выигрыш.

### 13.3 Сеть
- Автопереподключение с экспоненциальным backoff и jitter, resume по `seq`.
- Список адресов API/WS из конфигурации с запасными вариантами.
- Дедупликация запросов, отмена устаревших.

### 13.4 Платформы
- Адаптеры в `lib/platform/`: `web.ts` и `tauri.ts` с одним интерфейсом.
- Порядок: сначала веб-клиент (быстрее итерации), затем оболочка Tauri.
- Веб можно ставить как PWA на телефон до появления мобильных клиентов.

### 13.5 Бюджеты производительности
Размер бандла, время старта и память проверяются в CI; превышение бюджета блокирует мердж.

## 14. Устойчивость к блокировкам и хостинг
- Весь трафик по TLS на 443.
- Никаких зависимостей от внешних CDN, шрифтов, аналитики, сторонних скриптов.
- Клиент получает список адресов (основной и запасные домены), умеет переключаться.
- Уведомления: абстракция над Web Push / нативными каналами, чтобы не зависеть от одного провайдера.
- Продумать до запуска: страна хостинга и требования к хранению персональных данных (для пользователей из РФ есть требования локализации). Этот вопрос лучше уточнить у юриста.

---

## 15. Наблюдаемость, тесты, CI
- Структурные логи (slog), request-id, корреляция между API и WS.
- Метрики Prometheus: число WS-соединений, задержка рассылки (гистограмма), размеры очередей, ошибки, rate-limit срабатывания, задержки БД и Redis.
- Health/readiness-эндпоинты.
- Конфигурация через переменные окружения (12-factor).
- CI: линтеры, юнит- и интеграционные тесты (testcontainers: Postgres, Redis, MinIO), сборка клиента и проверка бюджетов.
- **Нагрузочные тесты** WS (k6 или собственная утилита на Go): сценарии массовых подключений, всплеска сообщений, массового реконнекта.

## 16. Функционал MVP (включён в UI)
Регистрация и вход, серверы и текстовые каналы, инвайты, сообщения в реальном времени, онлайн-статус, история с пагинацией, ответы на сообщения, правка и удаление своих сообщений, загрузка картинок.

Схема и протокол уже поддерживают, но в UI не включаем: реакции, ЛС, голосовые каналы, поиск, управление ролями.

---

## 17. План разработки (этапы)
1. Монорепо и docker-compose (Postgres, Redis, MinIO).
2. Схема БД, миграции, Snowflake, обоснование индексов.
3. Спецификация API и WS-протокола, генерация типов.
4. Бэкенд: auth, REST, права.
5. Бэкенд: WS-шлюз, Redis (pub/sub, streams, presence), resume.
6. Клиент (веб): каркас, адаптеры платформы, вход, серверы и каналы.
7. Клиент: чат с виртуализацией, оптимистичной отправкой, кэшем, переподключением.
8. Файлы (S3), ответы, правка и удаление.
9. Оболочка Tauri, сборки Windows и macOS.
10. Тесты, нагрузочный тест WS, метрики и бюджеты.

После MVP: голос (LiveKit), реакции, ЛС, роли в UI, поиск, мобильные клиенты.
